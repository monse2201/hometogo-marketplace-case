Problem Framing

The data layer is the product beneath every product surface.

The core challenge is not simply ingesting more supply. It is converting inconsistent partner representations into a canonical accommodation model that downstream systems can trust.

INPUT PROBLEM

Heterogeneous partner feeds

Different taxonomies, IDs, languages, update cadences, room structures, amenity labels, cancellation terms and location precision.

ENTITY PROBLEM

Property vs. unit vs. offer

The system must distinguish the physical property, bookable units and commercial offers. Incorrect modeling can create both false duplicates and incorrect merges.

DISTRIBUTION PROBLEM

Every surface inherits data quality

Search ranking, price comparison, booking, SEO, APIs and LLM retrieval can only be as reliable as the canonical catalog underneath them.

Product principle: one canonical catalog, multiple representations

I would avoid creating a separate “AI inventory” as the long-term architecture. The canonical property/unit/offer model should remain the source of truth, while embeddings, generated summaries and LLM-oriented representations are derived enrichment layers with provenance and confidence.

Hands-On Product Analytics

Challenge assumptions with queries, not gut feel.

A data infrastructure PM does not need to train the models, but should independently inspect catalog health, segment failures, validate hypotheses and translate analytical output into product decisions.

duplicate_rate_by_partner.sqlBigQuery-style SQL
SELECT
  partner_name,
  COUNT(*) AS total_listings,
  ROUND(
    COUNTIF(duplicate_flag = TRUE)
    / COUNT(*) * 100, 2
  ) AS duplicate_rate,
  AVG(match_confidence)
    AS avg_match_confidence
FROM marketplace.listings
WHERE listing_status = 'ACTIVE'
GROUP BY partner_name
ORDER BY duplicate_rate DESC;
quality_vs_conversion.sqlBigQuery-style SQL
WITH perf AS (
  SELECT
    listing_id,
    quality_score,
    COUNT(DISTINCT session_id) views,
    COUNTIF(booking_id IS NOT NULL) bookings
  FROM analytics.listing_sessions
  GROUP BY listing_id, quality_score
)
SELECT
  CASE
    WHEN quality_score >= 90 THEN '90-100'
    WHEN quality_score >= 80 THEN '80-89'
    WHEN quality_score >= 70 THEN '70-79'
    ELSE 'Below 70'
  END AS quality_band,
  SAFE_DIVIDE(
    SUM(bookings), SUM(views)
  ) AS conversion_rate
FROM perf
GROUP BY quality_band;

Product Judgment

Explicit trade-offs, measurable guardrails.

The goal is not to pretend there is one universally correct answer. It is to make the decision logic visible and define what evidence would change the decision.

01 · Precision or recall?

A false merge can combine genuinely different accommodations and corrupt content, price or availability. A missed match creates duplicate inventory. Those errors are not equally costly.

Starting decisionBias toward precision for automatic merges.
GuardrailUse confidence tiers for ambiguous candidates instead of a single binary policy.
Evidence that could change itIf missed duplicates materially hurt conversion while false merges remain extremely rare.

02 · Should every missing field reduce Quality Score equally?

No. Missing a decorative description sentence and missing exact location or availability have different traveler and commercial consequences.

Starting decisionWeight dimensions by traveler relevance and observed downstream impact.
GuardrailCritical accuracy failures cannot be offset by strong images or copy.
Evidence that could change itExperimentation and causal analysis showing different field-level effects.

03 · AI-specific inventory or stronger core model?

A parallel AI catalog can accelerate experiments but creates another source of truth. A stronger canonical model creates leverage across all surfaces.

Starting decisionCanonical model first; AI representations as derived enrichment.
GuardrailDo not block low-cost AI experiments while improving the foundation.
Evidence that could change itA distribution channel with materially different data semantics that cannot be derived safely.
Product Thesis

Marketplace data infrastructure is a growth product when its quality changes what travelers can discover and book.

The product owner's job is to make that leverage visible: define the data contract, evaluate ML trade-offs, create feedback loops, and connect infrastructure improvements to measurable marketplace outcomes.
